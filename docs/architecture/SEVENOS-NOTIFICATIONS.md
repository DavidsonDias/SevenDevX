# SevenDevX notifications

The current application is a single SevenDevX organization, not a multi-tenant SaaS. Operational events are delivered only to `user_roles.admin` recipients. Each history row, preference and device belongs to one authenticated administrator, with the existing native MFA requirement applied in RLS and registration. Registration is limited to ten devices per account. Administrators cannot read another user's push endpoints through the client. A future tenant model must supply an explicit membership resolver before deploying this dispatcher to multiple organizations; never broadcast across tenants.

## Paths and delivery semantics

- `/admin/notifications`: existing history, unread counter, read and delete controls. ProtectedRoute + MFA and RLS remain authoritative.
- `/admin/notifications/preferences`: categories actually produced by the application. In-app opt-out suppresses new notices and therefore their pushes; push opt-out leaves the internal history intact. Email is not implemented here.
- `/admin/notifications/diagnostics`: secure-context/support/permission/SW/current-key/local-and-server checks, own devices and own delivery states. Activation is not a receipt. Self-test targets exactly the supplied subscription owned by the verified caller and is limited to once per minute, with request UUID idempotency.
- `/admin/notifications/open/:id`: authenticates, loads only the current owner's notice, marks read and resolves an internal admin route. Target screens still enforce their own authorization. Another account cannot resolve the notice.

An INSERT records the internal notice independently of push. A trigger creates one job per subscription. Best-effort post-commit pg_net dispatch and a once-per-minute cron process at most five jobs per invocation. SKIP LOCKED leases avoid concurrent claims. Three attempts maximum, exponential delay, five-minute crash lease, one-hour delivery window. New subscriptions never backfill history. Existing unrelated scheduled mail/webhook jobs remain unchanged; no historical campaign or reminder was enabled.

`accepted` means the push service accepted the request, not delivery. `received` is recorded only after the Service Worker resolves showNotification and acknowledges with the job's random, day-limited capability. This proves browser handling, not that the human saw an OS banner. `clicked_at` is a separate acknowledgement. Lost acknowledgements can leave accepted deliveries unconfirmed. Web Push is at-least-once; a stable notification tag replaces duplicate presentations, but the application does not claim exactly-once OS delivery.

## Producers

Existing server-side producers remain connected: CRM contact registration, incoming contact message, project pipeline change, automation failure, role/audit events, operational incidents and suspicious own sessions. Contact and project links use actual SevenOS routes. Contact/message IDs and automation run IDs deduplicate repeat emissions; project transitions use project/transaction/stage identity. Automation transitions to failed now notify even when failure occurs after insertion. No marketing messages, real-client test sends, or arbitrary recipient/title/body API is exposed.

## Secrets and transport

New exclusive P-256 VAPID keys are generated by web-push inside the Edge runtime. They are stored in Vault as `sevenos_vapid_public_v1` and `sevenos_vapid_private_v1`, not reused from PsicoOne or a previous environment. No private key is returned or bundled. Only service_role can execute the Vault accessor/initializer RPCs. The public-key endpoint returns only public material and setup status.

A separate Vault HMAC key `sevenos_push_scheduler_v1` signs project/action/timestamp-scoped packets. The worker rejects packets older than 90 seconds. The cron queue never receives a service_role key or reusable signing secret, because managed pg_net queue read privileges cannot be narrowed in this project. Replaying a short-lived drain packet cannot select a recipient or create a notice; claims are idempotent and bounded. The public receipt endpoint has only a single-delivery capability and cannot read notifications or trigger sends.

Registration validates HTTPS push-service endpoints and key shape, uses auth.uid() instead of a body user ID, and cannot transfer another account's endpoint. Delivery revalidates ownership, current admin membership, category preference, endpoint and current VAPID key. 404/410 subscriptions are removed. Errors store a short code/job ID, never endpoint, message, JWT or key. Every lockscreen payload is generic. The existing single injectManifest worker handles both cache and push; no second worker is registered. Other open editors are preserved when a push click opens its authorized resolver.

## Validation and operations

Run `npm run typecheck`, the existing regression suite plus `scripts/notifications.test.mjs`, `npm run build`, and Edge type checks from an isolated Deno working directory (do not let Deno replace the npm project's node_modules). Transactional SQL fixtures verify ownership, registration, grants, idempotency, preference suppression, lease exclusion and receipt/acceptance races; all fixture records roll back.

To validate on a physical device: open the diagnostic route in the installed PWA, enable notifications by a user gesture, send the self-test, background the PWA, confirm the SevenDevX OS notification, tap it, and verify the intended authenticated screen. Repeat on another owned device/browser. iOS/iPadOS requires a compatible installed Home Screen web app; OS focus/battery settings can suppress banners. No full-device completion claim is valid before this test. The private key needs no user entry for the Vault-based deployment. VAPID rotation requires explicit re-enrollment of existing devices; never silently reuse a different application's credentials.
